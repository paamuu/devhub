# DevHub 产品需求文档（PRD）

-   文档版本：0.1
-   状态：已纳入 M0 评审决策，待原型与技术验证
-   产品代号：DevHub
-   产品定位：本地优先的开发项目模板与工作区管理客户端
-   适用阶段：V1.0 MVP 规划

------------------------------------------------------------------------

## 1. 文档目的

本文档定义 DevHub V1.0
的产品目标、用户场景、功能范围、信息架构、关键流程、业务规则和验收标准，作为后续技术设计、UI
设计和开发任务拆分的依据。

本阶段只完成产品设计，不启动 Electron 工程初始化。

## 2. 产品概述

### 2.1 产品定位

DevHub
是面向个人软件开发者的桌面工作台，用于集中管理可复用项目模板和实际开发项目，帮助开发者从已有模板快速创建新项目，并完成本地运行、IDE
打开和 Git/GitHub 仓库关联。

DevHub 不是 IDE，也不是完整的 Git 图形客户端。代码编辑仍由 VS
Code、WebStorm 等外部 IDE 完成；DevHub
负责项目资产、项目生命周期和常用开发操作的组织。

### 2.2 核心对象

-   **模板（Template）**：可重复使用的基础项目目录及其元数据、运行配置。首发登记本地目录，可记录 Git Remote 作为来源信息。
-   **项目（Project）**：实际开发中的独立项目目录。项目可以由模板创建，也可以直接导入。
-   **标签（Tag）**：用于组织和筛选模板、项目的元数据。
-   **预览配置（Preview
    Configuration）**：定义项目如何启动、停止、检测就绪状态及打开预览地址。
-   **Git 远程仓库（Remote）**：由项目目录中的 Git 仓库管理。DevHub
    提供操作入口和状态展示，不取代 Git 本身。

模板和项目必须是独立实体。模板更新不自动覆盖已创建项目。

### 2.3 目标用户

主要面向需要长期维护多种项目样板的个人开发者，例如：

-   Web 官网、营销站点和个人网站开发者。
-   Vue、React 等前端项目开发者。
-   微信小程序、跨端应用开发者。
-   管理后台、Node.js 服务和其他工程项目开发者。
-   维护多个技术栈、多个 GitHub 仓库的独立开发者。

### 2.4 用户核心问题

1.  模板散落在不同目录，难以查找和维护。
2.  每次创建新项目都需要手动复制、清理和初始化。
3.  不同类型项目的启动命令和预览方式不同。
4.  项目目录、IDE、运行状态和 GitHub 仓库之间缺少统一入口。
5.  用户移动或删除目录后，项目管理记录容易失效。
6.  模板与实际项目的代码和 Git 历史必须安全隔离。

## 3. 产品目标与非目标

### 3.1 V1.0 产品目标

首发平台为 Windows。阶段 1–3 是实施顺序，V1.0 发布需通过 §12 的验收。

-   在本地统一登记、分类、搜索模板和项目。
-   支持从模板创建完全独立的新项目。
-   支持模板和项目的增删改查。
-   支持 Web 类项目的本地启动、停止、重启和日志查看。
-   支持打开项目所在目录及配置的 IDE。
-   支持检测本地 Git 仓库、查看基础状态并关联 GitHub Remote。
-   所有业务元数据保存在本地，不依赖 DevHub 云服务。
-   客户端重启后，模板和项目记录能够恢复。

### 3.2 非目标（V1.0 不做）

-   云端账号、云端数据库和多设备自动同步。
-   多人协作、权限系统和团队工作区。
-   在线模板市场。
-   完整的 Git 图形化客户端、复杂合并冲突解决界面。
-   自动把模板更新合并到已有项目。
-   AI 生成项目或代码。
-   自建远程代码托管服务。
-   第一版内嵌浏览器作为主要预览方式。
-   保证所有小程序平台均可由 DevHub 直接预览。
-   在应用内 Clone 模板、为已导入目录初始化 Git、Commit / Pull / Push、自动探测 IDE、静态预览与应用内置项目运行时。

## 4. 产品原则

1.  **Local-First**：项目元数据、配置和日志默认保存在本机；网络只用于用户主动执行的
    Git/GitHub 操作。
2.  **不接管用户代码**：项目目录由用户控制，DevHub 不擅自修改项目源码。
3.  **模板与项目隔离**：从模板创建项目时，默认不继承模板的 `.git`
    历史和远程仓库。
4.  **显式授权**：运行项目脚本、删除实际目录、执行可能改变远程仓库状态的操作时，提供清晰确认。
5.  **可恢复**：路径失效、操作失败或应用异常退出时，尽量保留用户数据并提供恢复路径。
6.  **渐进扩展**：运行方式通过适配器和配置扩展，不把某一框架或命令写死在业务流程中。
7.  **设计质量**：UI 遵循 Anthropic `frontend-design` 的设计理念，建立
    DevHub 专属的 Developer Workbench 视觉方向，避免通用 SaaS Dashboard
    套版。

## 5. 信息架构与导航

建议 V1.0 主导航：

-   Dashboard
-   Templates
-   Projects
-   Settings

Preview 和 Git
操作优先放在项目详情页中；当运行中的项目管理需求明确后，再考虑独立的
Preview Manager 页面。

### 5.1 Dashboard

展示：

-   最近打开的项目。
-   最近使用的模板。
-   当前运行中的预览任务。
-   路径失效或需要处理的项目提示。
-   快速导入模板、创建项目的入口。

不以大量统计卡片为主要内容。首页的首要目标是帮助用户继续最近的工作。

### 5.2 Templates

支持：

-   模板列表、网格或紧凑列表展示。
-   名称搜索、类型筛选、标签筛选。
-   导入本地模板。
-   新建模板记录。
-   编辑模板元数据。
-   查看模板详情。
-   配置模板默认预览方式。
-   关联或查看模板来源仓库信息。
-   删除模板记录或删除模板目录（分开确认）。

模板详情至少展示：名称、描述、类型、技术栈、路径、标签、来源、预览配置、创建时间和最近检查时间。

### 5.3 Projects

支持：

-   项目列表及搜索、类型和标签筛选。
-   新建项目（从模板创建或导入已有目录）。
-   编辑项目元数据。
-   打开项目目录。
-   使用配置的 IDE 打开项目。
-   查看项目路径、来源模板和 Git 信息。
-   进入项目详情。
-   归档项目。
-   删除项目记录或删除项目目录（分开确认）。

### 5.4 Project Detail

建议采用清晰的分区或 Tab：

-   Overview：基本信息、路径、来源模板、最近打开时间。
-   Preview：启动配置、运行状态、预览地址和日志。
-   Git：仓库检测、Remote、分支、工作区状态和常用操作。
-   Settings：项目级运行配置和 IDE 配置。

### 5.5 Settings

V1.0 设置项：

-   默认模板目录和项目目录，用作选择器起点，允许登记独立目录。
-   手动配置 IDE 可执行文件或打开命令。项目配置优先于全局设置。
-   Git 可执行文件检测。
-   日志目录和保留策略。
-   数据备份与恢复。
-   UI 主题偏好（浅色、深色或跟随系统；最终选项待 UI 评审确认）。

### 6.3 从模板创建项目

创建向导至少包含：

1.  选择模板。
2.  输入项目名称。
3.  选择目标父目录。
4.  确认最终目标路径。
5.  选择 Git 初始化策略。
6.  检查目标路径是否已存在。
7.  显示复制和初始化结果。

Git 初始化策略：

-   不初始化 Git。
-   初始化新的本地 Git 仓库。
创建后可单独关联已有 Remote。已导入的非 Git 项目可在外部初始化，返回 DevHub 后重新检测。

V1.0 不默认自动创建 GitHub 仓库。若未来增加自动创建，需要单独的 GitHub
授权流程。

复制规则默认排除：

-   `.git/`
-   `node_modules/`
-   `dist/`
-   `build/`
-   `coverage/`
-   `.cache/`
-   `.turbo/`

默认排除 `.env`、`.env.*`（但保留 `.env.example`、`.env.sample`
和 `.env.template` 等示例文件）。排除规则应可查看，首发采用固定规则。复制时跳过 Git 元数据文件和目录、符号链接以及 Windows junction。

创建成功后，新项目必须拥有独立目录；若选择初始化 Git，则生成新的
`.git`，不得继承模板 Remote。

### 6.4 本地预览

  ID        需求                                 优先级
  --------- ------------------------------------ --------
  PVW-001   为项目配置启动命令、参数和工作目录   P0
  PVW-002   启动项目并捕获 stdout/stderr         P0
  PVW-003   停止由 DevHub 启动的进程             P0
  PVW-004   重启项目                             P1
  PVW-005   展示运行状态和运行日志               P0
  PVW-006   配置预览 URL 并打开默认浏览器        P0
  PVW-007   检测端口冲突并展示错误               P1
  PVW-008   通过就绪检测确认服务启动成功         P1
  PVW-009   多项目并行预览                       P1
  PVW-010   微信小程序等平台专用适配器           P2

第一版先支持通用命令启动的 Web 项目。微信开发者工具、uni-app
特定工作流和其他平台专用预览后续扩展。

每次显式启动或重启前展示命令、参数和工作目录并确认。预览工作目录限定在项目内，每项目最多一个活动会话。关闭 Windows 主窗口即退出应用，并停止所管理的进程。未配置就绪检测时显示进程已启动，配置检测时另行展示就绪或失败状态。

用户可以按项目配置自定义环境变量，并通过密钥引用向预览进程注入敏感值。界面显示密钥是否已配置，密钥值仅用于启动进程。

  GIT-001   检测项目是否为 Git 仓库                  P0
  GIT-002   获取和展示 Remote                        P0
  GIT-003   添加、修改和删除 Remote                  P0
  GIT-004   获取当前分支                             P1
  GIT-005   展示基础工作区状态                       P1
  GIT-006   查看最近提交记录                         P2
  GIT-007   Commit、Pull、Push                       P2
  GIT-008   在浏览器打开 GitHub 仓库                 P0
  GIT-009   GitHub CLI 登录状态检测                  P2

GitHub 认证优先复用系统 Git Credential Manager、SSH Agent 或用户已有的

### 6.6 数据与备份

-   **DAT-001（P0）**：数据库、自定义环境变量和加密密钥数据保存在用户主目录 `~/.devhub/`，Windows 对应 `%USERPROFILE%\.devhub\`。普通应用设置保存在本地 SQLite。
-   **DAT-002（P0）**：导出一致性备份，范围为 DevHub 元数据、非秘密设置和非秘密环境变量。默认排除密钥、项目及模板源码、预览日志和 Git 对象。
-   **DAT-003（P0）**：从受支持版本的备份恢复。恢复前展示覆盖范围并生成当前备份。恢复后重新检查路径，缺失密钥提示重新配置，重新执行运行确认。
-   应用升级时执行版本化数据库迁移。

## 7. 关键用户流程

### 7.1 导入模板

1.  用户进入 Templates。
2.  点击 Import Template。
3.  选择本地目录。
4.  DevHub 检查目录可读性，尝试识别项目特征。
5.  用户确认名称、类型、技术栈和描述。
6.  用户可选配置预览命令。
7.  保存模板记录。
8.  返回模板列表并显示导入结果。

失败场景：目录不存在、无读取权限、数据库写入失败、重复路径或重复登记。失败时不应留下半成品记录。

### 7.2 从模板创建项目

1.  用户选择模板并点击 Create Project。
2.  输入名称和目标目录。
3.  检查路径冲突及磁盘空间等可检测条件。
4.  显示文件排除规则和 Git 初始化策略。
5.  用户确认。
6.  DevHub 在临时目标目录执行复制。
7.  根据选择初始化新的 Git 仓库。
8.  将临时目录原子移动到最终目录（平台允许时）。
9.  创建数据库项目记录。
10. 展示结果并提供 Open Folder、Open IDE、Preview 等入口。

落位前失败或取消时清理可验证属于本次操作的临时目录。目录已落位而登记失败时保留目录，显示实际路径，并提供继续登记或保留目录的选项。不得覆盖或删除用户已有目标目录。

### 7.3 启动预览

1.  用户打开项目详情页。
2.  选择或确认预览配置。
3.  DevHub 展示命令、参数和工作目录。
4.  用户确认启动。
5.  Preview Manager 创建进程并订阅日志。
6.  有配置时执行就绪检测，并分别展示进程状态与服务可用状态。
7.  展示预览 URL，提供打开默认浏览器的操作。
8.  用户可打开浏览器、停止或重启。

启动失败时展示退出码、错误输出和建议检查项，不伪造运行成功状态。

### 7.4 关联 GitHub 仓库

1.  DevHub 检测项目是否为 Git 仓库。
2.  若不是，提示在外部初始化后重新检测；若只位于上级工作树中，显示实际工作树根并引导登记该根目录。
3.  用户输入 HTTPS 或 SSH Remote URL。
4.  DevHub 校验 URL 格式并展示将执行的操作。
5.  用户确认后添加 Remote。
6.  重新读取 Remote 并展示关联结果。
7.  认证和网络失败时展示 Git 原始错误的安全摘要。

### 7.5 路径重新关联

1.  DevHub 发现登记路径不存在。
2.  项目显示 Missing 状态，不自动删除。
3.  用户选择 Locate / Relink。
4.  用户选择新目录。
5.  DevHub 检查目录特征、Git 状态和可访问性。
6.  用户确认后更新路径。
7.  保留项目 ID、标签、描述和来源模板关系。

## 8. 业务规则与数据约束

1.  模板与项目使用不同 ID 和不同表。
2.  项目创建后与模板只保留来源关系，不建立自动同步关系。
3.  默认不复制模板 `.git` 目录。
4.  默认不复制依赖安装目录和构建产物。
5.  项目记录删除不等于项目目录删除。
6.  模板记录删除不等于模板目录删除。
7.  所有破坏性文件操作必须显示绝对路径并二次确认。
8.  项目路径应规范化并检测重复登记；符号链接和大小写敏感性需要按平台处理。
9.  预览运行状态是运行时状态，不应只依赖数据库中的历史状态。
10. Git Remote、分支和工作区状态以本地 Git
    仓库实时结果为准，数据库缓存只能用于展示优化。
11. 用户可以在 DevHub 外部修改项目；每次读取 Git 状态时应重新查询 Git。
12. 不在数据库中保存 GitHub 密码或明文 PAT。
13. 同一规范路径仅能登记一次。首发允许独立目录嵌套登记，涉及已登记的同址、父目录或子目录时禁止实际目录删除。
14. 预览运行期间须先停止该项目的活动会话，再删除记录、删除目录或重关联。目录移入系统回收站后保留登记并标记路径失效，失败时保留登记并展示错误。用户可另行删除登记记录。
15. 从模板创建项目成功后更新最近使用时间。删除模板记录时保留已有项目及其来源模板名称快照。
16. 归档项目保留目录与元数据，默认从活动列表隐藏，可在归档列表恢复。

## 9. UI/UX 设计要求

### 9.1 设计方法

遵循 Anthropic `frontend-design`
的设计理念：先确定产品的视觉方向和信息架构，再实现组件；避免默认化、模板化的
AI 后台视觉。

DevHub 的视觉方向定义为 **Developer Workbench**：

-   专业、克制、精密。
-   信息层级清晰，适度提高信息密度。
-   项目路径、技术栈、Git 状态和运行状态易于扫描。
-   交互反馈明确，操作状态可见。
-   装饰服务于任务，不为了视觉效果增加无意义卡片、渐变或动画。
-   支持键盘操作、焦点可见和合理的颜色对比度。

### 9.3 组件设计要求

-   统一按钮、输入、菜单、对话框、空状态、加载状态和错误状态。
-   组件需有 hover、focus、active、disabled 等状态。
-   列表支持清晰的空状态和错误状态。
-   危险操作应使用明确的文案，不只依赖颜色。
-   运行日志采用适合长内容的滚动区域，避免无限制渲染全部历史日志。
-   长列表后续可按实际规模增加虚拟滚动。

## 10. 非功能需求

### 10.1 性能

-   冷启动和列表加载应保持流畅；具体性能预算在原型和目标设备评估后确定。
-   不在主线程执行大规模文件复制、递归扫描或阻塞式 Git 操作。
-   日志应限制内存缓存大小并支持文件轮转。
-   大型项目目录扫描应可取消或异步执行。

### 10.2 可靠性

-   数据库使用事务保证关键元数据操作一致性。
-   项目复制采用临时目录和失败清理策略。
-   应用崩溃或退出后不应误删项目文件。
-   预览进程必须能够明确区分运行中、启动中、失败、停止中和已停止状态。

### 10.3 安全与隐私

-   默认不上传项目元数据或源码。
-   Renderer 不直接获得 Node.js 完整权限。
-   Preload 只暴露最小化 API。
-   命令执行需校验工作目录和参数。
-   对删除目录、执行脚本和远程 Git 操作进行明确确认。
-   敏感环境文件默认不从模板复制。

### 10.4 可维护性

-   业务规则与 Electron API 隔离。
-   文件系统、Git、进程管理通过适配层封装。
-   IPC 接口具备明确的类型和校验。
-   数据库迁移有版本号。
-   关键服务具备单元测试和集成测试。
